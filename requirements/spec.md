## 1. 产品概述

ai-chat 为多个用户提供 AI 对话服务：任何人可注册账号使用，对话经自建后端统一接入第三方大模型 API（OpenAI 兼容协议，DeepSeek/GLM），支持流式输出的多轮连贯对话；会话数据存储在服务端，同一账号多设备数据一致。产品定位为**多用户自部署 Web 服务**——单人即可部署、供多人注册使用的自托管服务。产品形态为**多用户自部署的 AI agent 对话服务**：除纯文本对话外，AI 可经服务端工具网关调用工具（首个生产工具为联网搜索，随 A2 交付），并将工具步骤与来源引用呈现给用户；上下文组装、回合编排与配额计量由服务端 agent 运行时承担（CHG-007，2026-08-17 方向升级）。RAG/知识库仍暂缓（见想法池）。

**架构决策（2026-08-15 CEO 拍板；CHG-004 已批准（2026-08-15，req-baseline-v3））**：应用为**前后端分离架构**——前端 Vue3 + TS + Vite 不变；新增 **Python FastAPI 后端**，职责：① 用户账号体系（注册/登录/会话管理，用户名+密码自管，不依赖第三方登录；**不保留未登录本地模式，必须登录**）；② API 密钥统一管理与服务端代管，**双模式**——默认服务端统一 key（配额内免费额度），高级设置允许用户自填 key 存服务端并解锁更高配额；③ OpenAI 兼容流式请求的代理转发；④ 用户数据（会话/供应商档案）云端存储；⑤ **agent 运行时**（CHG-007，2026-08-17）：ReAct 循环（最大步数/单步超时/断连取消三护栏）、工具网关（注册/参数校验/出网固定域白名单/超时/结果大小限制/注入防护）、SSE 事件协议 v2（服务端解析重组、独立回合端点，事件表见 changes.md CHG-007 内容 4.1）、上下文组装迁服务端（规则照搬：系统提示词 + 最近 20 轮）、配额按回合计——技术口径全文见 changes.md CHG-007。公开注册前提下，滥用防护与用量配额为上线必要条件（REQ-024，P0）；服务治理由 Web 管理后台承担（REQ-025，P1）。

**仓库布局（2026-08-15 CEO 拍板，CHG-004 实施层细化）**：同仓库 monorepo——后端代码置于本仓库新增 `backend/` 目录（Python/FastAPI，独立依赖文件与 lockfile，.gitignore 排除 `__pycache__`/`.venv`）；前端代码保持根目录现状不动；`docker-compose.yml` 放仓库根目录统一编排。不另建独立后端仓库、不用 submodule。

> 决策历史：2026-08-15（req-baseline-v1）曾拍板「纯前端应用直连第三方 API，不自建后端」；同日 CEO 决策升级为自建 FastAPI 后端（CHG-004），原决策由上文替换，原文存于变更历史（changes.md / git 历史）。2026-08-15 CHG-004 决策「联网搜索本轮不做」；2026-08-17 CEO 方向决策升级为 agent 架构，联网搜索作为第一个生产工具纳入（CHG-007），原文存变更历史与 docs/architecture-upgrade-plan-2026-08-17.md。

## 2. 用户故事

### REQ-001 发送消息并流式接收回复（CHG-007 改写：回合事件流）

- **用户故事**：作为用户，我要在输入框输入文本并发送，以便获得 AI 的回答，且回答以流式方式逐步显示，以便我不必等待完整生成。
- **描述**：对话主界面的核心交互：文本输入框 + 发送按钮 + 消息展示区。AI 回复以打字机效果流式渲染。
- **主流程**：
  1. 用户在输入框输入文本（支持多行）
  2. 点击发送按钮或按回车（Shift+Enter 换行）
  3. 用户消息立即显示在消息区，输入框清空
  4. AI 回复以**回合（turn）**为单位流式渲染：文本增量逐步显示（打字机效果不变）；模型调用工具时，消息流内出现工具步骤（运行中/完成/失败状态、可折叠、结果卡，REQ-032），工具结果返回后回答继续流式生成（CHG-007，基线 req-baseline-v5；deep-research 回合的事件流渲染归 REQ-047，模式开关为 ComposerBox 加法——CHG-012 波及注记，发送/停止交互零变化）
  5. 回合结束后，回复气泡标记为完成
- **异常分支**：
  - 输入为空或仅含空白字符：发送按钮不可用，点击无动作，不发出请求
  - 发送时上一条回复仍在生成中：禁用发送（或提示等待），不并发请求
  - 网络失败 / API 报错 / 超时：该 AI 气泡显示明确错误提示（含错误类型），并提供"重试"入口；用户已发出的消息保留在消息区，不丢失
  - 流式中断：已收到的部分内容保留显示，并标注"生成中断"
  - 工具步骤失败 / 单步超时：工具步骤卡标「失败/超时」，模型收到错误结果可降级直答，回合继续不崩（口径见 REQ-030 异常分支，CHG-007）
  - 回合被步数上限截停：回复末尾标注「已到单回合步数上限」，已生成内容保留（REQ-030）
  - 断连取消：服务端取消上游调用与工具执行，未完成回复标注「生成中断」（REQ-030）
- **验收标准**：
  - 输入"你好"并发送后，1 秒内用户消息出现在消息区
  - 收到首个流式数据块后 200ms 内，回复气泡开始显示内容
  - 回复过程中界面无需整体刷新，历史消息不重排闪烁
  - 发送空字符串 / 纯空格：无请求发出，无新气泡产生
  - 断网状态下发送：3 秒内出现含错误提示的气泡，且提供重试；重试成功后正常流式显示
  - 回合事件序逐帧断言见 REQ-030 验收 1（CHG-007 归位）；本条既有验收零回退
- **优先级**：P0（MVP）
- **涉及页面**：design/iter-1（已基线）

### REQ-002 多轮上下文记忆（CHG-007 改写：组装迁服务端；CHG-010 改写：三级压缩落地；CHG-011 改写：五层注入序）

- **用户故事**：作为用户，我要 AI 记住我在本会话中说过的话，以便进行多轮连贯对话而不必每次重复背景。
- **描述**（CHG-007 改写，基线 req-baseline-v5；CHG-009 波及指针，基线 req-baseline-v6；CHG-010 正式改写，基线 req-baseline-v7；CHG-011 正式改写，基线 req-baseline-v8）：上下文组装由**服务端 agent 运行时**执行（REQ-033，前端不再组装与上传历史）：服务端按会话存储的消息取**系统提示词（如有，见 REQ-008）+ 最近 20 轮（最多 40 条消息）**组装；**B1 起 system 段为静态/动态两段式分区（CHG-009/REQ-036，窗口规则不变）**；回合内工具结果注入当轮上下文、不占 20 轮窗口。**B2 起窗口规则演进为「20 轮窗口 + 三级压缩」（CHG-010/REQ-039）**：上一回合机器实测 prompt token 超阈值时，中段历史以摘要替代参与组装（旧工具结果先行裁剪）、最近 R 轮全文保留；**压缩只影响发给上游的内容——库内消息全文零删除，界面展示/导出/搜索口径全部不变**；未超阈值或压缩降级时，20 轮窗口现行口径零回退。**C 起组装新增用户长期记忆层（CHG-011/REQ-042）**：用户有记忆条目且未整体停用时，记忆作为独立 system 消息注入动态尾区之后、摘要/历史之前；记忆只影响发给上游的内容——记忆数据服务端独立存储，库内会话全文与界面展示/导出/搜索口径零交互；无记忆或停用时组装口径与基线 v7 等价。五层记忆体系（会话内全文→会话摘要→用户长期记忆→用户 systemPrompt→产品人设）的注入序由本条与 REQ-033/036/039/REQ-042 共同固化（CHG-011）。
- **主流程**：
  1. 用户发送第 N 条消息
  2. 服务端按上述规则组装请求上下文（前端仅上送本条消息，REQ-033）
  3. AI 回复与上文指代、事实保持连贯
- **异常分支**：
  - 会话消息超出 20 轮：自动截断，仅携带最近 20 轮，不报错、不中断对话；被截断轮次仍完整保留在本地与界面中（超阈值且压缩生效的会话，中段不再被丢弃而是以摘要参与组装，REQ-039；未超阈值或压缩降级仍按本条现行口径截断——CHG-010）
- **验收标准**：
  - 连续对话测试：第 1 轮告知"我叫小明"，第 5 轮问"我叫什么"，AI 回答包含"小明"
  - 第 10 轮对话的请求中可观测到包含此前轮次的消息（服务端 pytest 断言，MockTransport 捕获上游请求体——CHG-007 服务端化口径）
  - 第 30 轮对话的请求体中仅包含最近 20 轮消息（服务端 pytest 断言），对话仍正常进行，无报错；界面仍可滚动查看全部 30 轮
  - 第 31 轮请求体 ≤ X token 且第 1 轮关键事实仍可答对（= REQ-039 验收 5，双向引用；X 与测量法随 B2 T0 取证定死，CHG-010）
  - 新会话首回合请求体含该用户记忆注入消息（位置 = system[1] 之后、逐字 = 记忆页预览，= REQ-042 验收 1，双向引用——CHG-011）
- **优先级**：P0（MVP，立项书成功标准 1）
- **涉及页面**：不涉及（数据层逻辑，界面表现归 REQ-001/004）

### REQ-003 新建会话

- **用户故事**：作为用户，我要一键新建一个空白会话，以便开始一个与之前话题无关的新对话。
- **描述**：提供"新建会话"入口，创建空会话并切换为当前会话。
- **主流程**：
  1. 用户点击"新建会话"
  2. 系统创建空会话（自动命名，见 REQ-009），切换到空白对话界面
  3. 新会话出现在会话列表顶部
- **异常分支**：
  - 当前会话回复正在生成中：**中断生成**（CEO 已拍板），原会话中该回复保留已生成部分并标注"生成中断"，不后台继续
- **验收标准**：
  - 点击"新建会话"后 300ms 内界面切换为空白对话界面，输入框可输入
  - 新会话在会话列表可见，刷新页面后仍存在（依赖 REQ-006）
  - 连续新建 10 个会话，列表完整显示 10 条，无重复 ID
  - 生成中点击新建：原会话的回复停止增长且标注"生成中断"，新会话界面立即可输入
- **优先级**：P0（MVP）
- **涉及页面**：design/iter-1（已基线）+ design-iter-11（已基线，2026-08-16——新建钮随侧栏改版，点击清空搜索口径）

### REQ-004 查看历史会话并切换

- **用户故事**：作为用户，我要看到我的历史会话列表并点击任一会话恢复查看，以便回顾和继续之前的对话。
- **描述**：侧边（或顶部）会话列表展示全部历史会话，点击切换到该会话并完整展示其消息。生成中切换会话**不中断**：原会话在后台继续流式生成，完成后切回可见完整回复（CHG-001，2026-08-15 修改；原"中断并标注"仅保留给"生成中新建会话"场景，见 REQ-003）。
- **主流程**：
  1. 用户打开应用，会话列表按最近活跃时间倒序展示
  2. 点击任一会话
  3. 消息区加载该会话全部消息并定位到最新一条
- **异常分支**：
  - 无任何历史会话：显示空状态引导（如"点击新建会话开始对话"），不显示空白列表
  - 会话数据损坏 / 读取失败：该会话在列表中标注"无法读取"，不影响其他会话的展示与使用
  - 切换时原会话正在生成：不中断，原会话后台继续生成（CHG-001）；切回时可看到已生成的部分或完整回复
- **验收标准**：
  - 含 50 个会话、每会话 20 轮消息时，点击会话到消息完整渲染 < 1 秒，滚动到最新消息
  - 空态：无会话时显示引导文案，不出现 JS 报错
  - 切换会话后再切回，消息内容与切换前一致
- **优先级**：P0（MVP，立项书成功标准 2）
- **涉及页面**：design/iter-1（已基线）+ design-iter-11（已基线，2026-08-16——列表项单行化/时间分组载体）

### REQ-005 删除会话

- **用户故事**：作为用户，我要删除不需要的会话，以便保持会话列表整洁。
- **描述**：会话列表项提供删除操作，需二次确认以防误删。
- **主流程**：
  1. 用户在某会话上触发删除
  2. 弹出确认提示
  3. 确认后该会话从列表和本地存储中移除
  4. 若删除的是当前会话，自动切换到列表中最近的会话；若已无会话，显示空态
- **异常分支**：
  - 取消确认：会话保留，无任何变化
  - 删除后本地存储写入失败：界面提示删除失败，会话保留
- **验收标准**：
  - 删除必须经确认，未确认前会话不被移除
  - 删除后刷新页面，该会话不再出现（本地存储中确实清除）
  - 删除当前会话后界面不出现空白或报错，按上述规则切换
- **优先级**：P0（MVP）
- **涉及页面**：design/iter-1（已基线）+ design-iter-11（已基线，2026-08-16——删除入口迁列表项「···」菜单）

### REQ-006 会话持久化与恢复（服务端存储；CHG-007 改写：v2 blocks）

- **用户故事**：作为用户，我要我的会话在关闭应用后依然保存，以便下次打开继续，不丢任何内容。
- **描述**（CHG-004 改写；CHG-004 已批准（2026-08-15，req-baseline-v3））：会话（含消息、branches 分支）的**唯一持久层为服务端数据库**；消息模型升级为 v2 blocks（CHG-007/REQ-032，基线 req-baseline-v5）——**新格式写档带会话 JSON 顶层 `schema: 2` 标记，存量 string 会话不迁移、读时归一化**；读写经 REQ-022 的云存储与同步承载（含跨格式写侧守卫）。浏览器 IndexedDB **不再作为运行时存储**，仅保留一次性角色：**v0.4.0 及以前旧版本本地数据的迁移数据源**，配合「导入本地会话到云端」入口（REQ-022）使用；导入完成后本地数据保留只读 30 天再自动清除。**必须登录后才能使用**：未登录只能看到登录页（REQ-020），本地不再产生新的会话数据。
- **主流程**：
  1. 用户登录（REQ-020），前端从服务端加载会话列表与数据
  2. 每轮对话完成后写回服务端（REQ-022）
  3. 关闭浏览器/换设备重新登录，会话列表与消息完整恢复

### REQ-020 注册与登录（用户名+密码，会话 token）〔CHG-004〕

  3. 校验通过后创建账号，直接登录进入主界面

- **异常分支**：
  - 用户名已被占用：注册失败，提示「用户名已存在」，不创建账号（唯一性大小写不敏感）
  - 用户名不合法（长度不在 2~32 字符、含中文/字母/数字/`_`/`-` 之外的字符）：前后端均拦截并提示规则，不提交

  - 两次密码不一致：提示，不提交
  - 登录时用户名或密码错误：统一提示「用户名或密码错误」，不区分具体是哪项错、不泄露账号是否存在
  - 注册/登录触发频率限制（REQ-024）：返回限制提示

- **验收标准**：
  - 新用户名注册成功后 3 秒内进入主界面，刷新页面仍保持登录态
  - 相同用户名二次注册：返回「用户名已存在」，数据库用户数不增加；注册「Alice」成功后再以「alice」注册：同样提示「用户名已存在」（大小写不敏感）
  - 输入 1 字符、33 字符、含 `@` 的用户名注册：前后端均被拦截并提示规则
  - 数据库中检索不到任何密码明文（密码字段均为哈希值）
  - 密码错误登录：3 秒内出现统一错误提示
  - 手动使 token 失效后发送消息：收到 401 并跳转登录页
- **优先级**：P0（CEO 已确认）
- **涉及页面**：design/iter-6（已基线，2026-08-15 CEO 批准；登录/注册原型承载，NCR-iter6-006 补记见 changes.md CHG-004 澄清定案 9）

### REQ-021 账号管理（修改密码、注销账号）〔CHG-004〕

### REQ-022 服务端会话云存储与多设备同步〔CHG-004；CHG-007 守卫〕

- **用户故事**：作为用户，我要我的会话保存在服务端并在所有登录设备上保持一致，以便换设备继续对话且数据不丢失。
- **描述**（CHG-004 已批准（2026-08-15，req-baseline-v3））：登录用户的会话（含消息、branches 分支、系统提示词、供应商档案）存储于后端数据库，为唯一持久层（承接 REQ-006）；前端打开时从服务端加载，每轮对话完成/变更后写回。多设备并发修改同一会话的冲突策略为**同代格式内最后写入覆盖（LWW，CEO 已拍板）**：被覆盖端下次加载以后端数据为准，不弹冲突解决 UI。**跨格式写侧守卫（CHG-007 定夺②，基线 req-baseline-v5）**：服务端 PUT 检测『存量已带 `schema: 2` 标记、来件为无标记旧格式（升级窗口期旧客户端陈旧副本）』→ 返回 409 `session_schema_conflict` 拒绝写入、存量逐字不动，防旧客户端覆盖抹掉新格式工具步骤。旧客户端遇 409 不重试（前端暂存队列 4xx 非临时性语义：首次保存静默上抛告警、队列重放按毒丸丢弃——代码取证存档 changes.md CHG-007）；新客户端恒带标记、理论不触发，防御性按 REQ-007 错误体系提示并引导刷新页面。提供**一次性「导入本地会话到云端」迁移入口**（面向 v0.4.0 及以前的本地数据）：导入后本地数据保留只读 30 天再自动清除。**不保留未登录本地模式（必须登录）**。
- **主流程**：
  1. 用户登录成功，前端从服务端拉取其会话列表与数据
  2. 对话、重命名、删除、编辑、版本切换等操作同步写入服务端（对应 REQ-001~019 的既有交互，仅数据读写层换源）
  3. 另一设备登录同一账号，刷新后看到相同会话列表与内容
- **异常分支**：
  - 拉取会话失败（网络/服务异常）：提示并可重试，不显示空白假象
  - 写回失败：本地暂存并自动重试；连续失败提示「部分更改未同步」
  - 多设备并发修改同一会话：按 LWW 覆盖，不报错、不弹冲突 UI
  - 多设备新旧客户端并存（升级窗口期）：旧格式载荷覆盖新格式存量 → 409 拒绝（见上守卫）；新格式覆盖旧格式 → 正常保存（升级）；同格式并发 → LWW 照旧（CHG-007）
  - 会话数量/体量大：列表分页或增量加载（阈值由性能测试定）
  - 迁移导入：过程可取消；本地会话作为**新增**导入，不覆盖云端已有会话
- **验收标准**：
  - 设备 A 完成一轮对话后，设备 B 登录并刷新，5 秒内可见该会话且内容逐字一致
  - 设备 A 删除会话，设备 B 刷新后该会话消失
  - 断网状态下完成的一轮对话，恢复网络后自动同步到服务端，另一设备可见
  - 两设备同时修改同一会话标题：后保存者生效，另一端刷新后与后端一致（LWW）
  - 旧版本本地 10 个会话经迁移入口导入后，云端会话数与内容一致；导入后本地数据只读、30 天后被清除（可观测）
  - LWW 守卫（CHG-007）：① v2 存量 + 无标记 v1 载荷 → 409 且 GET 复读存量逐字不变（pytest）；② 带标记整档透传回写（模拟老客户端 GET v2 后改名回写）→ 200 保存、blocks 与标记保留（pytest）
- **优先级**：P0（CEO 已确认）
- **涉及页面**：迁移入口 design-iter-8（已基线，2026-08-16——提示条/导入中可取消/完成只读 30 天说明/失败重试）

### REQ-030 工具调用框架与 ReAct 循环（含内置演示工具）〔CHG-007〕

- **描述**（CHG-007 新增，基线 req-baseline-v5）：后端 agent 运行时以「回合（turn）」为单位编排一次用户发送触发的完整过程：上下文准备（REQ-033）→ 流式调用上游（携工具定义）→ 解析工具调用意图 → 经工具网关执行（REQ-031）→ 工具结果回填 → 继续调用或终止。三护栏：**最大步数 = 10（普通回合；deep-research 回合独立上限 max_research_steps=16 与回合总时长护栏 900s——CHG-012/REQ-046，定夺⑥）**、**单步超时**（上游调用 120s、工具执行按各工具声明）、**断连取消**（客户端断开 → 取消进行中的上游调用与工具执行，无孤儿任务）——三项护栏参数均随 design-iter-13 基线定案（2026-08-17，九项定夺全按推荐）。事件经 SSE 协议 v2 下发（事件表与帧格式见 changes.md CHG-007 内容 4.1）。本条交付 2 个内置演示工具（echo / demo_weather，定义见 CHG-007 内容 4.6）作为无出网的循环验证载体，**终端可见性仅 admin**（design-iter-13 定夺④；档案「支持工具」开关 UI 随 A2/design-iter-14 落地）。上游错误映射完全复用 REQ-007 / design-iter-7 §3.1 既有 10 场景体系，不新建映射。**CHG-009/B1 起回合内每次上游调用落请求级遥测（REQ-037），SSE v2 事件流与 usage 帧口径不变。CHG-010/B2 起回合受理时的组装已经三级压缩管道（REQ-039）：SSE v2 事件流对用户零变化（不新增事件类型），摘要调用不占回合 step 序列。CHG-012（基线 req-baseline-v9）：SSE 流新增心跳注释帧（`: ping`，连接层保活——非事件、前端零感知，REQ-045）；turn.end reason 枚举加法扩展 'time_limit'（deep-research 时长护栏终态，REQ-046）；事件类型枚举不变（deep-research 首版以既有九事件承载）。**
- **主流程**：
  1. 前端将**仅本条用户消息** + 会话 id POST 至回合端点（独立端点 `/api/chat/turn`，design-iter-13 定夺；历史不上传，见 REQ-033）
  2. 后端校验会话 token → 按回合计检查配额（REQ-034；不足即 429，零上游调用）→ 创建回合（turn_id）并下发 `turn.start`
  3. 服务端自库取会话消息 → 归一化（v1/v2 统一展开）→ 组装上下文（系统提示词 + 最近 20 轮）+ 注册表工具定义 → 首次上游流式调用
  4. 上游文本 delta 逐块转发为 `text.delta`；上游发起工具调用 → 下发 `tool.call` → 工具网关执行（校验链见 REQ-031）→ 下发 `tool.result`（含 ok/error/timeout 状态与耗时）
  5. 工具结果以 tool role 消息回填本轮上下文 → 步数 +1（下发 `turn.step`）→ 未到步数上限且模型仍要求调用工具 → 回到 4；模型给出最终回答或到上限 → 定型
  6. 回合结束：下发 `usage`（回合内 tokens 累计）→ `turn.end`（reason=done/max_steps/aborted/error）；assistant 消息以 blocks 落库（REQ-032），usage 落 usage_daily（REQ-034）
- **异常分支（逐项，含用户所见）**：
  - 入参异常（空文本/超长）：422 拒绝；前端本就禁发空输入（REQ-001），双保险
  - 上游报错（401/403/429/5xx/超时）：沿 REQ-007 既有映射——错误气泡（含类型与建议动作）+ 可重试错误提供重试；本回合已生成的文本与工具步骤保留
  - 上游连接中断：沿用既有 `upstream_interrupted` 自定义帧 → 已收内容保留、标注「生成中断」
  - 工具执行报错/超时：`tool.result` 带 error/timeout → 工具步骤卡标「失败/超时」；错误结果回填模型，模型可降级直答（回合继续，不崩）；连续工具失败无独立熔断（由步数上限兜底）
  - 步数到顶：回合终止（turn.end reason=max_steps）→ 回复末尾标注「已到单回合步数上限」（文案随 design-iter-13），已生成内容保留并落库
  - 断连取消：用户关闭页面/断网 → 服务端检测连接断开，取消进行中的上游调用与工具执行；已落库内容保留，未完成回复标注「生成中断」（与 REQ-006 刷新恢复口径衔接）；回合计费：已抵上游则计 1 回合、零上游调用的取消不计（design-iter-13 定夺）

  1. 模型判定需要搜索 → tool.call(search, {query}[, days])——**days（1~30，可选，CHG-008 增补 2026-08-18）**：强时效查询由模型自行限定「最近 N 天」（配合 REQ-033 系统段当前时间行判定），透传搜索 API `topic=news + days` 时间窗；不传维持综合搜索不限时

  4. tool.result 回填 → 模型综合生成带引用标记的回答 → 前端渲染引用来源卡（design-iter-14）
- **异常分支（含用户所见）**：

  - 搜索结果为空：模型据空结果如实回答「未搜到相关内容」，不编造来源
  - 结果超限：网关截断（模型只见截断后内容）

  1. 〔原表 11〕时效性问题（预置样例）回答含可见工具步骤与引用来源（真实 Chrome 走查留档）
  2. 〔原表 12-a〕搜索 API 失败/超时（假搜索端点）→ 回合降级直答不崩（pytest + 走查）

  4. 〔原表 9 实例化〕出网仅搜索 API 域：目标改为内网/他域 → 零连接（pytest）
  5. 搜索结果超限截断实例化用例（假端点返回超大结果 → 截断标注）

- **用户故事**：作为用户，我要长对话不再「超过 20 轮就失忆」——中段历史被自动压缩成摘要继续参与组装、开头关键信息保留，以便三十轮会话仍连贯，且请求体不随轮数无限膨胀。
- **描述**（CHG-010 新增，基线 req-baseline-v7）：在 REQ-033 服务端组装器与 REQ-036 分区基础上，上下文组装升级为**三级压缩管道**（审核稿 §三要素 6 三级口径）：**一级 snip（旧工具结果裁剪）**——组装时确定性地把早于最近 K 条工具消息（K=2，定夺⑨定案）的 tool 结果替换为裁剪占位（文案 `[旧工具结果已裁剪：{工具名} · {状态}]`，后端拥有、逐字断言面登记 verify 文档）；**二级 compact（中段历史摘要）**——以一次上游摘要调用把水位之前的中段历史压缩为摘要文本，作为**独立 system 消息**注入组装，挂载点 = system[1] 动态尾区之后、历史之前（REQ-036 预留注入区落地，changes.md CHG-010 内容 3.1）；**三级 token 阈值自动触发**——以该会话上一回合 step=1 上游调用的 telemetry `tokens_prompt` **机器实测值**（REQ-037 数据底座，不引入 tokenizer、不估算）判定，超阈值（定夺③定案：T0 取证后定死，实施期暂以 32768 占位）即在下一回合组装前执行 compact。**压缩只影响「发给上游的内容」**：库内会话消息全文零删除，界面全量展示/导出/搜索/版本分支口径全部不变（定夺⑥定案口径）。摘要产物存服务端独立表 `context_summary`（迁移 v9，定夺⑤定案，changes.md CHG-010 内容 3.2），不写回会话档，与 LWW/409 守卫/整档透传零交互。摘要调用跟随回合当前模式（统一 key → .env 统一三变量；自填 → 生效档案三要素），模型名随模式默认、不引入独立配置面（定夺②定案）。摘要调用为非流式调用、独立超时护栏 30s（定夺⑨定案）；任何失败降级为不压缩组装（20 轮窗口 + snip），回合不阻塞、用户无感。摘要调用 tokens 如实计入回合 token 累计（REQ-034 既有口径自然覆盖，定夺⑧定案）；压缩执行落 telemetry `kind='compress'` 行（机器采集，铁律 5，行口径见 REQ-041）。摘要基建（调用器 + 产物存储 + 水位语义）为 C 期记忆体系复用面（审核稿 §三要素 6 末句）。**本条产出的会话摘要 = C 五层记忆体系第 2 层「会话摘要」（CHG-011 注记，基线 req-baseline-v8：管道/阈值/水位口径零变化，仅纳入五层叙事；注入位置维持动态尾区之后，记忆消息挂载于其前）。**
- **主流程**：
  1. 回合受理 → 自库读会话档 → `wire_messages_from_doc` 归一化（零变化）→ 一级 snip：早于最近 2 条工具消息的 tool 结果替换为裁剪占位
  2. 阈值判定：读该会话上一回合 step=1 的 telemetry `tokens_prompt` 机器实测值 → 未超阈值 / 无记录（新会话/遥测缺失）→ 按基线 v6 口径组装（20 轮窗口，零回退）
  3. 超阈值且有有效摘要（水位消息仍在当前 messages 中）→ 摘要注入组装：system[0]（如有）+ system[1] + 摘要 system 消息 + 最近 R 轮（R=5，定夺⑨定案；snip 已执行）
  4. 超阈值且无有效摘要 → 执行摘要调用（非流式、30s 护栏）→ 产物与水位落 `context_summary` 表、落 compress 行 → 按 3 组装
  5. 无可压缩中段（总轮数 ≤ R）→ 跳过 compact（提示面见 REQ-040「无需压缩」口径）
- **异常分支**：
  - 摘要调用失败/超时/空摘要/上游 4xx/5xx：本回合回退不压缩组装（20 轮窗口 + snip），回合正常完成；warning 日志 + compress 行 status=error/timeout（铁律 5 如实记，不阻塞、不扰用户）
  - 无上一回合遥测记录（新会话/遥测写失败/90 天清理边界）：按未超阈值处理（保守方向 = 不差于现状，不造数）
  - 编辑重建（REQ-015）删除了水位消息（编辑点在水位处或之前）：摘要行删除失效，下次超阈值重新生成（changes.md CHG-010 内容 3.2）
  - 版本切换（REQ-019）分支激活：水位消息 id 在当前 messages 中不存在 → 视同失效，回退不压缩组装（branches 本不参与组装，零新增口径）
  - 自填档案上游不支持/拒绝摘要调用：同失败分支降级（不区分错误形态，降级方向恒为现状）
  - 阈值超限但请求体仍超上游硬上限（极端大会话）：上游报错沿 REQ-007/030 既有错误映射（本条不另设分支；R 轮与摘要长度参数以 T0 取证校准避免该形态成为常态）
- **验收标准（可判定）**：
  1. snip 确定性：构造含 5 个工具回合的会话 → 组装请求体中仅最近 2 条 tool 消息保留结果全文，更早 tool 结果为裁剪占位文案（逐字断言，pytest + MockTransport 捕获）
  2. 自动触发：置上一回合 step=1 telemetry tokens_prompt = 阈值+1 → 本回合请求体含摘要 system 消息（挂载位置 = system[1] 之后、历史之前）且历史仅最近 R=5 轮（pytest，摘要调用以假上游编排）
  3. 阈值下零回退：纯文本会话 + tokens_prompt = 阈值-1 → 组装与基线 v6 口径逐字段等价（REQ-033/036 既有验收复跑；含旧工具回合的会话按验收 1 口径断言，改写映射登记）
  4. 失败降级：假摘要调用 500 / 超时 → 请求体回退不压缩形态、回合正常完成、turn.end 帧正常、compress 行 status=error/timeout（pytest）
  5. 30 轮验收（审核稿 B2 口径）：30 轮会话（第 1 轮预置关键事实，如「我叫小明」+ 一项需求）→ 第 31 次请求体 ≤ X token（X 与测量法随 T0 取证定死，定夺⑦定案：测量 = 假上游 usage 帧 prompt_tokens 机器读数，铁律 5，不手数 token）且第 31 轮回答断言包含关键事实（pytest 脚本化假上游；真实 DeepSeek 30 轮冒烟走查留档 T0 取证段）
  6. 存储语义：压缩执行前后 chat_sessions 会话档 messages 数量与全文逐字不变、GET 读路径输出不变（pytest 前后比对）
  7. 产物独立：压缩产物仅存 context_summary 表；会话 PUT 载荷形状零变化、不含摘要字段（vitest 断言 PUT 载荷 + pytest 断言产物表）
- **优先级**：P0（CHG-010 建议，CEO 已批准）｜**批次**：B2（iter-16 候选）
- **涉及页面**：不涉及（纯后端数据层，用户界面零变化）

### REQ-040 用户手动压缩入口与可见性〔CHG-010〕

- **用户故事**：作为用户，我要能主动压缩某个长会话的上下文并看到执行结果，以便在感觉 AI「变啰嗦/忘事」或切换话题时立即整理上下文，不必等阈值自动触发。

- **主流程**：
  1. 用户在会话列表项「···」菜单（或 design-iter-16 定稿形态）触发「压缩上下文」
  2. 前端 POST /api/chat/compact → 服务端鉴权与会话归属校验（沿复合主键隔离）→ 执行管道（摘要调用同 REQ-039 口径）

- **异常分支**：

  - 该会话正在生成回合：拒绝并提示稍后（409 语义，防并发组装竞态，形态随设计）

- **验收标准（可判定）**：
  1. 手动压缩执行一次 → compact 端点落 compress 行（endpoint='compact'，turn_id=NULL）、context_summary 更新、usage_daily turns 零变化（pytest + test_quota 零改动复跑）

  4. 归属隔离：他人 session_id → 404；普通用户操作正常、无 admin 门槛（pytest）
  5. design-iter-16 走查清单留档（亮/暗双主题 + 执行中态 + 失败态 + 无需压缩态，v1.4.10 B/v1.4.11 B 断言面）
- **优先级**：P1（CHG-010 建议，CEO 已批准）｜**批次**：B2（iter-16 候选）

### REQ-041 压缩效果度量与可观测〔CHG-010〕

- **用户故事**：作为服务部署者，我要压缩执行次数、压缩前后 token 规模与降幅被机器度量并在 admin 可见，以便 B2 的效果可验证、摘要调用成本如实入账（审核稿 §九「运营者算得清每块钱花在哪」的 B2 面；铁律 5：度量只允许机器采集）。
- **描述**（CHG-010 新增，基线 req-baseline-v7）：迁移 **v9** 两项加法：① telemetry 表增列 `tokens_before` / `tokens_after`（仅 kind='compress' 行取值，存量行 NULL、不回填）；② 新建 `context_summary` 产物表（REQ-039 载体，schema 见 changes.md CHG-010 内容 3.2，与 v9 同批落库）。每次压缩执行（回合内自动 / 手动）落一条 compress 行（kind='compress'：turn_id 自动回合关联 / 手动 NULL，endpoint='turn'/'compact'，model=摘要模型，latency_ms=摘要调用耗时，status，摘要调用自身 token 消耗记 tokens_prompt 同列口径，tokens_before=触发依据的机器实测值，tokens_after=压缩后首次 step=1 上游调用 usage 机器实测值**懒回填**——未测得记 NULL、聚合显示缺失，不估算）。compress 行不占回合 step 序列（llm 行 step 连续性口径零变化，REQ-037 验收 1 不回退）。admin 遥测聚合（REQ-038 `GET /api/admin/telemetry` 端点）加法扩展：**压缩次数**与**平均降幅**（1 − Σtokens_after/Σtokens_before，任一侧缺失该时段显示缺失标注）；**成本聚合计入 compress 行 tokens**（摘要调用如实入账，统一 key 模式口径同 REQ-038 定夺⑥）。REQ-037/038 既有行形状与口径零回退。
- **主流程**：压缩执行 → compress 行创建（tokens_after=NULL）→ 该会话下一次 step=1 上游调用返回 usage → 独立短连接懒回填 tokens_after（失败不阻塞、不补造）→ admin 遥测视图按日聚合展示压缩次数/降幅。
- **异常分支**：tokens_after 始终未测得（会话再无回合）→ 维持 NULL，聚合显示缺失；压缩失败行（status=error/timeout）照常落、不计入降幅聚合（只计次数）；普通用户访问聚合端点 → 403（沿 get_admin_user 门禁，REQ-038 口径零变化）。
- **验收标准（可判定）**：
  1. compress 行完整性：一次自动压缩回合结束 → telemetry 恰 1 条 compress 行，tokens_before 等于触发依据值、tokens_after 与该会话下一回合 step=1 llm 行 tokens_prompt 一致（pytest）
  2. 配额数据面零回退：test_quota 全套零改动复跑全绿（usage_daily 落账不变）；REQ-037 既有 test_telemetry 全绿（行形状仅加法列）
  3. 聚合一致性：造数已知 compress 行集 → 聚合端点次数/降幅精确值断言；缺失 → 缺失标注（pytest）；成本聚合含 compress 行 tokens（数值断言）
  4. 普通用户访问扩展后的聚合端点 403 且不泄露数据（pytest）
  5. design-iter-16 走查清单 admin 面留档（压缩卡 + 缺失态，亮/暗双主题）
- **优先级**：P1（CHG-010 建议，CEO 已批准）｜**批次**：B2（iter-16 候选）
- **涉及页面**：design-iter-16（已基线，2026-08-20 CEO 批准——admin 遥测视图扩展形态，与 REQ-040 同稿承载）

### REQ-045 SSE 心跳与长回合连接保持〔CHG-012〕

- **用户故事**：作为用户，我要 AI 回合（尤其深度研究这类多步长回合）在长时间思考与工具执行期间连接不被中间层掐断，以便研究进度不中断、长回答完整送达。
- **描述**（CHG-012 新增，基线 req-baseline-v9）：回合 SSE 流新增**心跳机制**：服务端在流式响应中周期性下发 SSE 标准注释帧（`: ping\n\n`），间隔 `heartbeat_interval` 默认 20s（.env 可覆盖；T0 以本地 nginx 反代默认 proxy_read_timeout 60s 实测定档，取约 1/3 余量）。**注释帧不是事件**：前端 parseSse 只认 `data:` 行（client.ts L95-107 现状取证），注释帧天然跳过——前端零改动、blocks 与事件序零影响。心跳对**全部回合生效**（普通回合同样受益：上游单步超时 120s > 反代 60s 的静默窗口现状已存在，deep-research 步数多仅放大暴露面，连接层修复不分模式——定夺⑩推荐）。实现 = stream() 协程内 watchdog 周期补发注释帧（有事件产出的时段注释帧可省略或照常，帧本身无害；注释帧不参与事件序断言、不落遥测）。断连取消口径零变化（心跳不改变 CancelledError 传播，REQ-030 既有语义）。
- **主流程**：
  1. 回合受理 → SSE 流建立 → watchdog 启动
  2. 事件产出间隔 < 心跳间隔：事件照常下发，watchdog 周期到点补注释帧（与事件帧交错）
  3. 客户端/反代在任意两个数据帧之间持续收到注释帧 → 空闲超时不触发 → 连接保持
- **异常分支**：
  - watchdog 自身异常：不杀流（事件照常下发），warning 日志——心跳是尽力而为的保活，不构成回合成败要件
  - 心跳间隔配置非法（≤0）：按默认值 20s 处理（保守方向，不拒启动）
  - 断连：现行断连取消口径零变化（REQ-030），心跳随流终止
- **验收标准（可判定）**：
  1. 静默保活：假上游 45s 无 delta 的回合 → SSE 原始字节流含 ≥2 个 `:` 前缀注释帧、相邻注释帧间隔 ≤ heartbeat_interval + 5s（pytest 原始字节断言；事件序断言不含注释帧）
  2. 前端零感知：同一字节流经 parseSse → 零事件产出、blocks 零变化（vitest；注释帧不进 TurnEvent）
  3. 普通回合零回退：delta 密集回合心跳在流中存在但事件序不变（REQ-030 验收 1 复跑全绿）
  4. 反代实测：本地 nginx（默认 proxy_read_timeout 60s）反代下 90s 静默流不断连（T0 取证留档 verify + 走查脚本一条）
- **优先级**：P0（CHG-012 建议，CEO 已批准——连接正确性 + deep-research 前置）｜**批次**：D1（iter-18 候选）
- **涉及页面**：不涉及（连接层，用户无感知）
