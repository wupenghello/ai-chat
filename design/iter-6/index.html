4未登录应用框架说明（REQ-006 门禁 · REQ-020 路由守卫与回跳）

spec REQ-006 改写条款：「必须登录后才能使用：未登录只能看到登录页，本地不再产生新的会话数据」； REQ-020 异常分支：「会话 token 过期/无效：受保护请求返回 401，前端跳转登录页；登录后回到之前的页面」。 本节为应用框架说明（CHG-004 影响评估要求随 T0 交付）——主界面本身沿用 iter-1~5 基线，本稿不重画； 唯一一处基线增量 = 侧栏底栏登出入口（4.2，第 9 节定案 5，2026-08-15 CEO 批准）。

401 闭环（使用中失效）：③ 中任意请求返回 401（token 过期/改密使失效）→ 跳 /login?redirect=当前路由， 登录页顶部显示 warning banner「登录已过期，请重新登录」→ 重新登录后回跳原路由继续，未发出的输入不丢失。
守卫规则（T2 实现口径）：vue-router beforeEach——未登录（无有效会话）访问任何功能路由 → replace 到 /login?redirect=…；已登录访问 /login → 直接 replace 到主界面（已登录不再看登录页）； 守卫判定依据「会话是否有效」（应用启动时调 /api/me 探测 + 请求中 401 兜底，具体由 T1/T2 定，设计不约束实现）。
redirect 安全：redirect 参数仅接受站内相对路径（拒绝外站 URL 与协议相对地址，防 open redirect），非法值回退到 /。
未登录零写入（REQ-006 验收子集）：未登录状态下浏览器 IndexedDB 不产生任何新的会话数据写入（旧版本遗留数据原样保留， 迁移入口 iter-8）。
登录成功即终点：登录/注册成功无中间确认页、无欢迎页——直接回跳原路由或进入主界面（最快路径）。 登出：入口 = 侧栏底栏最小扩展（4.2，第 9 节定案 5，2026-08-15 CEO 批准的 iter-1~5 基线唯一增量）；登出后回到 ①（跳登录页）。

5HttpOnly Cookie 与防 CSRF 技术注记（T1 开发对齐）

token 传递方式已定案（2026-08-15 CEO 定）：HttpOnly Cookie，同源部署前提，前端不做 token 管理。 本节为设计基线随附的技术说明——设计层的结论是用户基本无感：无授权弹窗、无跨站跳转、无 token 相关 UI； 用户唯一感知点 = 会话过期后操作收到 401 → 跳登录页（第 4 节 401 闭环）。具体实现以 T1 技术说明为准，此处为设计侧建议基线。
5.1 设计层用户感知对照HttpOnly Cookie 方案下用户看到什么
场景用户感知（设计结论）
登录成功后无感知——浏览器静默保存会话 cookie，直接进入主界面（第 4 节）
刷新 / 关闭浏览器重开（有效期内）无感知——同源请求自动携带 cookie，保持登录态（REQ-020 验收「刷新页面仍保持登录态」）
会话过期 / token 失效后操作唯一感知点——收到 401 跳登录页 + warning banner「登录已过期，请重新登录」，登录后回跳原路由
跨站站点伪造请求（CSRF 攻击面）无感知且无入口——SameSite 阻断跨站携带 cookie（见 5.2），界面无任何相关提示
登出会话失效 + 清除 cookie，跳回登录页（入口 = 侧栏底栏，见 4.2 定案 5）
前端零 token 管理（定案口径）：前端代码不读取、不解析、不存储任何 token（HttpOnly 对 JS 不可见；不用 localStorage 存 token， 降低 XSS 取 token 面）；所有请求同源相对路径（/api/…），凭证由浏览器自动携带。
5.2 后端 SameSite 策略建议（写入设计基线供 T1 对齐）最终以 T1 技术说明为准
Set-Cookie: session=<opaque-id>; HttpOnly; SameSite=Lax; Path=/ # 生产启用 HTTPS 后追加 Secure（云部署为 CHG-004「后续待定」，本地 Compose 阶段不加） # 开发环境：Vite dev server 以 proxy 将 /api 转发至 backend 容器 —— 前后端始终同源（iter-6 风险清单口径）
SameSite=Lax 理由：同源请求与普通站内导航自动携带 cookie（登录态延续不受影响）；跨站 POST 不携带—— 经典 CSRF（外部站点伪造表单/请求 POST 本站写接口）因 cookie 缺席被服务端 401 拒绝，配合「写操作仅 POST/PUT/DELETE + JSON body」 （Lax 下跨站顶层 GET 导航虽携带 cookie，但读接口无副作用），基本免疫 CSRF，无需引入 CSRF token 或校验 Origin 的额外复杂度。 若 T1 评估后认为需要更强的 Origin/Referer 白名单校验作为纵深防御，属实现增强，不改变设计层「用户无感」结论。
同源部署前提（定案）：docker-compose 单入口（前端构建产物 + backend/），开发期 Vite proxy——两端点永不同源跨域， 规避跨域 credentials 配置问题；iter-7 全链路 Compose 沿用此前提。
登出语义：后端使会话失效（服务端会话记录删除/标记，T1 验收「登出后 401」）+ 下发过期 cookie 清除；前端仅跳转登录页，不做本地清理动作。

编号问题定案内容（2026-08-15 CEO 定）
1 用户名规则 spec 未定义（REQ-020 仅定了密码最短 8 位），前后端需要同一条规则 已定案：2~32 个字符；允许中文/字母/数字/下划线/连字符；禁空格与其他符号；唯一性大小写不敏感。前端 regex 与后端 Pydantic 共用同一规则与同一组边界测试值。同步写入 spec REQ-020（由需求分析师落盘）。
2 错误提示色调语义：封禁/过期/限频用红还是琥珀？ 已定案：拒绝类=红（凭证错误、已占用、限频、网络）；状态类=琥珀（登录已过期、封禁）——非用户输入错误用琥珀，避免「我输错了」的误导。
3 登录/注册页移动适配是否作为正式承诺？（spec 非功能「兼容」现写「移动端 P1 不承诺」） 已定案：仅登录/注册两页承诺 ≤480px 窄屏可用，作为正式兼容性承诺（本稿第 6 节，登录页是移动端最常到达页面）；主界面移动适配维持 P1 不承诺。spec 兼容条款按此更新（由需求分析师落盘）。
4 登录/注册成功的反馈：直接进主界面，还是加「欢迎回来」toast？ 已定案：不加 toast，直接进——最快路径，利于「3 秒内进入主界面」验收；主界面本身加载会话列表即是「已登录」的强反馈。
5 登出入口在哪承载？（T1 有登出 API，但主界面基线本稿不动） 已定案：CEO 批准最小扩展——侧栏底栏加用户名 + 登出 icon 按钮（结构示意与参数见 4.2，26px ghost、底栏 56px 结构不动）；这是 iter-1~5 主界面基线在本迭代的唯一一处增量，T2 按此实现。
6 「忘记密码」口径：spec 无邮箱体系下无法自助找回 已定案：登录页不放「忘记密码」链接（避免死链）；找回 = 管理员重置，留待 iter-8 管理后台（REQ-025）承载。
7 密码输入是否提供明文显隐切换？ 已定案：提供（眼睛 icon 按钮，沿用 iter-5 设置页 key-eye 模式；登录/注册全部密码字段同样提供）。
