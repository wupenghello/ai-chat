定案记录（CEO，2026-08-16，4 项全部按建议方案定案）
① 统一 key 存放口径——按建议定案：backend/.env 三变量（AI_CHAT_UNIFIED_KEY / AI_CHAT_UNIFIED_BASE_URL / AI_CHAT_UNIFIED_MODEL，默认上游 DeepSeek），.env 不入 git + .env.example 占位；

③ 上游错误透传映射——按建议定案：第 3 节映射表随基线批准即生效（T1/T2 按表实现）；

编号问题（iter-7.md T0 原文）定案内容（2026-08-16 CEO 定 = 建议方案）
① 统一 key 及默认上游的存放与环境变量口径（.env 不入 git） 已定案：backend/.env 环境变量：AI_CHAT_UNIFIED_KEY / AI_CHAT_UNIFIED_BASE_URL / AI_CHAT_UNIFIED_MODEL 三项 （默认上游 DeepSeek，与 T1 冒烟计划一致）；.env 加入 .gitignore 不入 git，仓库提供 .env.example 占位说明各项含义。 理由：12-factor 惯例、Compose 部署时环境注入天然支持（iter-8 全链路 Compose 直接受益）、泄露面收敛为部署机文件权限； 缺配时后端返回「服务端未配置统一密钥」（第 3 节映射表已定稿文案）。
② 自填 key 服务端受保护存储形式 已定案：SQLite 明文 + 文件权限起步，不做应用层可逆加密。理由：单机自部署威胁模型下，可逆加密的密钥仍须存于同机（env/密钥文件）， 对「能读 DB 文件的攻击者」仅增加一层混淆、无法真正对抗，却引入密钥轮换/备份恢复复杂度与调试成本。 「受保护」拆解为可验收条款：key 不进 git（全量历史可检索验证）、不进日志（日志脱钩）、不出现在任何 API 响应（只回掩码）、 DB 文件依赖部署目录属主与权限（0600）——iter-7 风险清单已列 Code Review 重点审密钥路径。 备选（未采纳，留档）：AES-GCM 加密存储、密钥来自 env——其对本机攻击者防护有限，且增加备份/迁移复杂度。 未来多租户云化时再升级 KMS 方案。
③ 上游错误经代理透传后的 REQ-007 文案映射表 已定案：第 3 节映射表定稿生效（10 类场景 + 1 条消亡分支留档，含 iter-8 配额占位行）——T1/T2 按表实现，无需另行定夺。
④ 存量本地档案上云方式（登录静默自动 vs 手动导入） 已定案：手动导入（非静默）：登录后提示条 + 一键导入（2.3 示意样件）——API key 属敏感凭据，未经用户确认不得上传； 「暂不导入」本次会话不再提示、下次登录仍显示；导入=本地档案作新增写入云端（不覆盖已有，口径同 REQ-022 会话迁移）+ 本地清除。 形态本稿定稿，落地排 iter-8（与 REQ-022 存量迁移同批）。
